# v6 参考资源的 CPU 压缩（2026-09-15）

停止参考 LUT 的质量迭代。v6 的 41 波长烘焙及 RGB 导出已经完成；本轮没有新烘焙或 PT。保留原始光谱资源作为教师，压缩从已有 Rec.2020 节点导出开始。v6 的参考误差没有因压缩测试而变成“已验收”。

已接入 demo 的保守版本为 `out/lut_reference_v6_packed16`。它保留全部 **126,978,560 个采样点**、坐标映射、太阳表和原有非线性插值；LUT 常驻载荷为 **469,745,860 字节（469.75 MB / 447.98 MiB）**，比 RGB f32 减少 **69.55%**。相较原始 41 波长显示路径，约减少 45 倍。

这里的显存数字是 GPU buffer 载荷，不是整个进程的显存。还需画面、RGB 累加、PT 参照、交换链和驱动内存；仅 3840×2160 的输出与累加两个资源合计约 265 MB。已有光谱启动路径会同时上传全部波长，约需 21.08 GB，这解释了为何大资源容易在启动时耗尽显存；未能追溯用户当时的确切启动参数。

## 实测体积与编码

|方案|常驻 LUT 载荷，十进制 MB|说明|
|---|---:|---|
|41 波长 f32|约 21,082|保留为 CPU 教师/烘焙原件|
|RGB f32|1,542.62|包括三个太阳衰减表|
|Packed，16 点一块|**469.75**|本轮选择|
|Packed，32 点一块|492.63|解码节点与 16 点版本逐位相同|
|Packed，64 点一块|561.04|块内值跨度增大，抵消了头部减少的收益|

编码保留符号、8 位指数和 11 位尾数，按最近值舍入。它比 f16 多一位尾数，并保留 f32 的指数范围，避免暗部因半精度指数范围而大面积归零。每块分别保存三个通道的最小整数编码，用块内所需的位宽存差值，最后共享完全相同的编码块。16 点版本共 7,936,160 块，5,935,063 个唯一块。

GPU 随机访问只读块索引和整数数据，重建 f32，再执行原来的 PCHIP/log 插值；没有启动时全量解压，没有在编码值上做纹理过滤，也没有减少角度或海拔采样。太阳衰减表仍是原始 f32。普通有限值的尾数舍入上界约 0.0244%；接近 f32 最大有限值时的饱和例外上界约 0.0488%，当前资源远未接近这一范围。

本机缓存已热时，三个全量 CPU 打包实验分别约 8.27 / 7.45 / 7.21 秒，包含读取、编码、全节点解码核对和文件写入；不含命令结束前再次读盘校验。它们并非严格的独占性能基准，16 点实验与 CPU 质量检查存在时间重叠。

## 质量检查：分开计算编码误差与 RGB 导出误差

所有 **380,935,680 个通道值**都经过实际整数解码器核对，结果与预期舍入逐位相同。全节点最大通道相对误差为 **0.024408%**（分母下限 1e-30）；零值和微小负值没有被整体截断。

另外构建 **82,856 个非网格查询**：中午、47° 太阳、夕阳、蓝调、12 km 暮光、30 km 地影、120 km 大气边缘、400 km 轨道，以及最高约 22,025 km 的随机海拔。每个固定场景的一半方向集中在几何地平线 ±3°，另加太阳周围及 ±20°、±30° 的密集方向。先按原有映射解码和插值，再比较 RGB 向量。

## BC6H 为什么暂时没有作为默认格式

BC6H 的硬件格式是每 4×4 像素 16 字节。[Microsoft 格式说明](https://learn.microsoft.com/en-us/windows/uwp/graphics-concepts/bc6h-format)。本轮采用 [Intel ISPC 的 Rust 封装](https://docs.rs/intel_tex_2/0.5.0/intel_tex_2/bc6h/index.html)进行 CPU 编码，用 [bcdec_rs](https://docs.rs/bcdec_rs/0.2.0/bcdec_rs/)独立解码。

测试三种块排列，每种 32,768 个随机块：16 个相位节点、4 相位×4 观察方向、4 相位×4 太阳节点。每块先按共同的 2 的整数次幂缩放，再编码半精度输入；如此避免简单地将原始值直接变成 f16 时的动态范围问题。块内仍可能跨越强梯度或黑区。

较好的 `phase16 + slow` 结果：**块内最差 RGB 相对误差**的中位数 0.340%、P95 9.51%、P99 24.40%。这里是每块最差点的统计，不是整幅天空像素 P99，不能与上面的非网格查询百分位混为一谈。若要求块内每个通道误差 ≤1%（通道分母至少为 RGB 长度的 1%），仍有约 **36.6%** 的块需要高精度回退。慢速搜索相较快速编码改善有限。

此排列在全尺寸上预计需约 **134.39 MB BC6H + 33.60 MB 缩放表 + 18.87 MB 太阳表 = 186.86 MB**，但当前直接编码的质量不足以替换参考显示资源。这个数字是由块数推算的布局成本，未生成或接入全尺寸 BC6H 资源。原始纯 BC6H 纹理最低约 127 MB 的数字不含边缘填充、缩放和太阳表，不能当成完整资源预算。

## 后续 CPU 研究路线

当前 470 MB 版本是保留参考质量的压缩基线，还不是最终实时预算。下一步优先用参考烘焙器在目标布局上合成 RGB 数据，然后比较：

1. 相位方向的预测编码或自适应样条，降低块内差值位宽；仍可在 CPU 上测随机查询和地平线/太阳方向的误差。
2. 固定参数下的低秩角度/太阳矩阵，配局部残差；秩必须用非网格查询和时间、海拔连续性验证，不能只看拟合节点。
3. 对归一化后的平滑主体或残差应用 BC6H，并为极暗值、太阳峰、地影过渡保留高精度补丁。先计入补丁和索引的完整体积，再决定是否优于自定义编码。

本轮没有测压缩格式的完整帧率、实时 GPU 解码吞吐或最终低秩压缩率。自定义随机读取可能增加每次查表开销；CPU 压缩速度不能代替实时性能测试。

当前打包资源用于天空/地面边界辐亮度与太阳显示。它没有实现有限线段的视距雾或体积光。原始光谱光学厚度表继续保留在参考目录中，未复制进压缩显示资源；后续需要单独合成和验证有限线段透射/内散射表示。

## 接入及验证

demo 默认 `--lut` 已改为 `out/lut_reference_v6_packed16`，直接上传压缩 buffer。新增 `--lut-budget-mib`，默认 1024：在创建 GPU 设备之前检查 LUT 载荷，避免误选 21 GB 光谱目录后才发生显存分配失败。它不是对设备可用显存的自动检测；0 可关闭此检查，帧缓冲等额外内存仍需预留。

```powershell
cargo run --release -p sky-atmosphere-lut -- compress-rgb out/lut_reference_v6_rgb --out out/new_packed --block-texels 16
cargo run --release -p sky-atmosphere-lut -- inspect out/lut_reference_v6_packed16 --verify
cargo run --release -p sky-realtime-demo -- --experiment offline-lut --asset out/pt_noon_085/asset.json
```

完成 17 个相关 CPU 测试、LUT crate 全目标严格 Clippy、demo 编译，以及 512×384 的实际 demo 小图验证。另用实际 GPU 整数解码器核对 **199,680 个通道查询，逐位差异 0**。GPU 仅用于这些短显示/解码检查，没有执行传输求解。demo 的严格 Clippy 仍有既有的两个 `too_many_arguments` 警告，未修改无关接口。
